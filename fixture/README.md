# The fixture: two snapshots with a planted history

Generated by `generate.js` with a fixed seed; regenerating reproduces every committed file byte for byte (a test asserts it). The Salesforce side is records in REST query shape plus change events in CometD message shape, 30 days deep; the ERP side is records per entity plus an audit log; `EXPECTED_VERDICTS.json` holds the verdict, cause and stale side every planted row must receive, and the orphans. `force-app/` is the SFDX source of the Salesforce end of the bridge, uncompiled (no org in the build).

Sizes: 397 Salesforce records and 398 ERP records, 395 joined records, 14 contract fields, 2 with no declared owner, 2765 compared fields, 159 field writes from change events, 169 field writes from the audit log. Both snapshots are as of the start of 2026-11-10 UTC; the contract's window is 72 hours and its tolerance 5 seconds.

Every record starts converged on both sides. Each scenario below claims a record and a field nobody else has claimed, writes the history on one or both sides, and sets the snapshot values to the last write on each side, so the history is consistent with both snapshots (a test checks every field with a write).

## The SFDX source

- `objects/Sync_Change__e`: a high-volume platform event (`eventType` HighVolume, `publishBehavior` PublishAfterCommit) with six fields, one change per message.
- `platformEventChannelMembers/ChangeEvents_AccountChangeEvent`, `ChangeEvents_ContactChangeEvent`: Change Data Capture enabled on the two objects the contract names; these are the events the referee reads.
- `triggers/AccountSyncPublisher`, `ContactSyncPublisher`: publish a `Sync_Change__e` per changed contract field after the save, unless the change was committed by the integration user (an echo of the ERP), which is the same rule the referee applies offline.
- `triggers/SyncChangeSubscriber`: applies published events to the ERP in batches of 50 with a resume checkpoint, so an outage resumes within the 72-hour retention rather than from the start of it.
- `classes/SyncOutboundService`: the callout through `callout:External_CRM`, whose named credential and OAuth external credential add the Authorization header.
- `classes/SyncInboundResource`: `@RestResource(urlMapping='/sync/v1/*')`, the ERP's way into Salesforce; it commits as the integration user and refuses fields outside the contract.
- `classes/SyncContract`: the field lists and the integration user Id, the Apex twin of `contract/sync-contract.json`.
- `externalCredentials/External_CRM`, `namedCredentials/External_CRM`: the OAuth client-credentials configuration; the client id and secret are populated in the org, never in source.
- Three test classes with `HttpCalloutMock` and `RestContext` setups. None of this is compiled in the build; the referee never reads it.
